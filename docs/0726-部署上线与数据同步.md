## 〇、日常部署：一键脚本（已验证，2026-07-26）

**首次部署已完成并踩平所有坑后，以后日常部署只需两条命令**：

```bash
# 1. 确认配置文件存在（首次部署时已创建，日常不用改）
#    scripts/deploy.config.sh —— 含服务器 IP/目录/pm2 名

# 2. 一键部署
bash scripts/deploy.local.sh
```

脚本会自动完成：本地 build → 打包 → scp 上传 → ssh 触发服务器部署（解压+装依赖+建表+灌数据+重启）。

**灵活控制**（编辑 `scripts/deploy.config.sh` 的开关）：
- `DEPLOY_MIGRATE=true/false` —— 是否跑 `migrate deploy`（纯前端改动设 false）
- `DEPLOY_SEED_GUIDE=true/false` —— 是否灌 guide 数据（不更新指南内容设 false）
- `DEPLOY_SEED_FORCE=true/false` —— seed 是否覆盖（⚠️ true 会覆盖线上编辑过的内容）

### 首次部署踩过的坑（已全部固化进脚本/配置，日常不再踩）

| 坑 | 现象 | 固化方式 |
|----|------|---------|
| 宝塔 Node PATH | ssh 触发 `pnpm not found` | deploy.server.sh 动态扫描 `/www/server/nodejs/*/bin` |
| npm 包国外源超时 | `ERR_PNPM_META_FETCH_FAIL` | deploy.server.sh 自动 `pnpm config set registry npmmirror` |
| Prisma 引擎国外源超时 | `prisma generate` 卡 `Downloading 0%` | deploy.server.sh 自动 `export PRISMA_ENGINES_MIRROR=npmmirror` |
| `--prod` 跳过 devDep | `prisma`/`tsx: command not found` | package.json 把 prisma/tsx 挪到 dependencies |
| 装到 Prisma 7.x | `url property no longer supported` | package.json 固定 `prisma ^5.22.0`（别升 7） |
| DB drift 状态 | `P3018 relation "users" already exists` | deploy.server.sh 检测失败自动 `migrate resolve --applied` |
| LE 续签被 Next.js 拦截 | 验证 URL 404 | Nginx 加 `^~ /.well-known/` 强匹配（手动配一次） |
| LE 续签 SERVFAIL | 根域 NS/A 查不到 | 阿里云 DNS 补 `@` 根域 A 记录（手动配一次） |

后两个（Nginx + DNS）是**一次性手动配置**，配过就不用再管；前 6 个已全部脚本固化。

## 一、先理解数据同步的本质

### 你担心的"数据同步"其实很简单

**关键事实**：Agent 指南是**独立的新表**，和线上已有的博文/用户/评论**零数据交叉**。

| 维度 | 线上已有（绝对不动） | 本次新增 |
|------|---------------------|---------|
| 表 | `users` `posts` `categories` `tags` `comments` `post_view_events` | `guide_chapters` `guide_series_config` |
| 数据 | 你所有的博文、评论、用户 | Agent 指南 11 章 + 系列配置 |
| 迁移文件 | `20251230_init` `20260413_add_post_view_tracking` | `20260723_add_guide_models` |

**唯一引用关系**（非数据修改）：`guide_chapters.authorId` 外键指向 `users.id`——新表**引用** users，但不改 users 表结构和数据。

**所以"数据同步"= 只做两件事**：
1. 在服务器 DB 建 2 张新表（跑 `migrate deploy`，只增不减，旧表零影响）
2. 把本地打磨好的 Agent 指南内容灌进新表（跑 `seed-guide`，幂等，不碰任何旧表）

线上博文/评论/用户**一根毛都不会动**。

### 那为什么不直接导出本地 DB 导入服务器？

可以，但**风险大**：本地 DB 也有自己的 users/posts/comments（开发测试数据），全量导出会覆盖线上的真实数据。**正确做法是只迁移 guide 两张表的数据**，用 seed 脚本精准灌入。

## 三、完整部署流程（6 步）

### Step 0：本地准备（确认代码可构建）

```bash
# 在项目根目录
pnpm install
pnpm build          # 本地构建，确认无报错（2C2G 服务器跑不动，所以本地 build）
```

**必须确认 build 通过**——服务器只是解压，不会再 build。

### Step 1：本地打包（关键：要带 `docs/agent-guide/`！）

```bash
tar -czf release.tgz .next package.json pnpm-lock.yaml prisma docs/agent-guide
```

⚠️ **比旧文档多一个 `docs/agent-guide`**——因为服务器要跑 `seed-guide`，而 seed 读 `docs/agent-guide/manifest.ts` + `*.md`。不带这个目录，服务器 seed 编译失败或正文为空。

> 也可以不带 docs，改成"本地 seed 完再导出 SQL"——但跨库导数据更复杂，不推荐。带 docs 让服务器自己 seed 最简单。

### Step 2：上传到服务器

```bash
scp release.tgz root@<SERVER_IP>:<SERVER_DIR>/
```

### Step 3：服务器解压 + 装依赖

```bash
ssh root@<SERVER_IP>
cd <SERVER_DIR>
tar -xzf release.tgz
pnpm install --prod --frozen-lockfile   # 只装生产依赖（不带 devDependencies，省内存）
```

> 如果 `pnpm install` 也卡死（2C2G 装依赖也吃力），加 `--prefer-offline` 或先 `pnpm config set registry https://registry.npmjs.org/` 切官方源。

### Step 4：服务器配 `.env`（关键！）

编辑服务器 `<SERVER_DIR>/.env`，**确认/修改**这几项：

```bash
# ⚠️ 必须指向服务器自己的 postgres，不是本地 Docker
PRISMA_DATABASE_URL="postgresql://<线上用户>:<线上密码>@<线上host>:<端口>/blog_platform?schema=public"
DATABASE_URL="postgresql://<线上用户>:<线上密码>@<线上host>:<端口>/blog_platform?schema=public"

JWT_SECRET="<线上已有的JWT，别动>"
NEXT_PUBLIC_BASE_URL="http://<SERVER_IP>"   # 或你的域名

# OSS（本次新增，图片上传用）
OSS_REGION="oss-cn-guangzhou"
OSS_BUCKET="<OSS_BUCKET>"
OSS_ACCESS_KEY_ID="<RAM子账号AK>"
OSS_ACCESS_KEY_SECRET="<RAM子账号SK>"
OSS_USE_INTERNAL="true"   # ⚠️ 服务器设 true，走内网免流量费
```

**坑 1（最重要）**：`PRISMA_DATABASE_URL` 必须是**线上真实 DB 地址**。你本地 `.env` 里写的是 `127.0.0.1:5432`（本地 Docker），服务器上如果 postgres 也是同机 Docker，那 `127.0.0.1` 可能也对——但**必须先 ssh 上去确认**：
```bash
# 服务器上确认 postgres 在跑
docker ps | grep postgres          # 如果用 Docker
# 或
systemctl status postgresql        # 如果直装
# 确认能连上
psql -h 127.0.0.1 -U <用户> -d blog_platform -c "SELECT 1"
```

### Step 5：服务器建表 + 灌 Agent 指南数据（核心步骤）

```bash
cd <SERVER_DIR>

# ① 应用迁移：只建 guide_chapters + guide_series_config 两张新表
#    （migrate deploy 只跑未应用的迁移，旧迁移已 baseline，不会重跑）
npx prisma migrate deploy

# ② 灌 Agent 指南内容（幂等：只插新章，不覆盖任何已存在数据）
pnpm db:seed:guide
#    ⚠️ 不要加 --force！--force 会覆盖已编辑数据。本次首次部署加不加都行，
#       但养成"不加 --force"的习惯，避免以后误覆盖线上 admin 编辑的内容
```

**预期 seed 输出**：
```
✅ 入库 11 章节中（其中 4 章可访问、7 章 WIP）
✅ 系列配置 singleton 已建
```

**验证数据进去了**：
```bash
# 服务器上直接查
psql -h 127.0.0.1 -U <用户> -d blog_platform -c "SELECT slug, title, published FROM guide_chapters ORDER BY \"order\";"
# 应看到 11 行
psql -h 127.0.0.1 -U <用户> -d blog_platform -c "SELECT title FROM guide_series_config;"
# 应看到 1 行 singleton
```

### Step 6：重启服务 + 验证

```bash
pm2 restart <PM2_NAME> --update-env   # --update-env 确保读到新加的 OSS_* 变量
pm2 logs <PM2_NAME> --lines 20        # 看启动日志有无报错
```

**线上验证清单**：
- [ ] `http://<SERVER_IP>/` → 跳转到 `/blog`
- [ ] `http://<SERVER_IP>/blog` → 首页顶部有 Agent 指南卡片
- [ ] `http://<SERVER_IP>/agent-guide` → 总览页（含系列配置文案）
- [ ] `http://<SERVER_IP>/agent-guide/intro` → 卷首（带 SVG 转型图）
- [ ] `http://<SERVER_IP>/agent-guide/phase-0-terminology` → 术语地基（4 张 SVG）
- [ ] `http://<SERVER_IP>/agent-guide/phase-1-mindset` → 心智迁移（5 张 SVG）
- [ ] `http://<SERVER_IP>/agent-guide/phase-2-python`（WIP）→ 应该 404
- [ ] 登录 admin → `/admin/guide` → 看到 11 章列表
- [ ] admin 编辑一篇章节 → 前端立即生效（revalidatePath）

## 四、迁移环境坑（来自 0723 文档，服务器首次部署可能遇到）

### 坑 2：服务器 DB 可能也是 drift 状态

你本地 DB 之前是 drift（有迁移文件但无 `_prisma_migrations` 历史表，早期用 `db push` 建的）。**服务器 DB 大概率也是同样的 drift 状态**（如果当初也是 `db push` 建的）。

**现象**：服务器跑 `migrate deploy` 报：
```
P3005: database schema is not empty
```
或
```
P3008: Migration ... is already applied but not found in migration history
```

**解决方案**（首次部署时执行一次 baseline，之后不用再管）：

```bash
cd <SERVER_DIR>

# 1. 先把已有的两个旧迁移标记为"已应用"（不真正执行，只写历史表）
npx prisma migrate resolve --applied 20251230174814_init
npx prisma migrate resolve --applied 20260413205000_add_post_view_tracking

# 2. 再 deploy，这次只会应用新的 add_guide_models 迁移
npx prisma migrate deploy

# 3. 重新生成 client
npx prisma generate
```

**判断要不要 baseline**：先直接跑 `migrate deploy`，如果报 P3005/P3008 就按上面 baseline；如果直接成功就跳过这步。

### 坑 3：服务器 Node 版本

本项目要求 Node 20.x。服务器上确认：
```bash
node -v   # 应该是 v20.x
```
如果是 18.x，sharp（图片处理）可能有问题。升级 Node：
```bash
# 用 nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
nvm install 20
nvm use 20
```

## 五、数据同步的备选方案（如果 seed 方式不合适）

### 方案 A（推荐）：seed-guide 脚本（本文档主方案）
- **怎么做**：服务器跑 `pnpm db:seed:guide`，从打包带上来的 `docs/agent-guide/` 读数据灌库
- **优点**：幂等、安全（不碰旧表）、可重复跑、内容更新时改 md 重跑即可
- **缺点**：服务器要有 `docs/agent-guide/` 目录（打包时带上即可）

### 方案 B：导出本地 guide 表数据为 SQL，服务器导入
- **怎么做**：本地 `pg_dump -t guide_chapters -t guide_series_config > guide-data.sql`，scp 上传，服务器 `psql < guide-data.sql`
- **优点**：不依赖 docs 目录，精确控制
- **缺点**：要处理 `authorId` 不一致问题（本地 admin 的 id 和服务器 admin 的 id 不同！guide_chapters.authorId 外键会失效）
- **不推荐**：authorId 跨库不一致是巨坑，除非你能保证两边 admin 用户 id 相同

### 方案 C：通过线上 admin 后台手动建
- **怎么做**：部署后登录线上 `/admin/guide/new`，一篇篇手动建
- **优点**：零数据同步风险
- **缺点**：11 篇 + 系列配置，手动建累死，且容易抄错
- **适合**：只发 2-3 篇的情况

**结论：用方案 A（seed-guide）**。

## 六、后续内容更新（部署后怎么改 Agent 指南）

部署成功后，Agent 指南内容在服务器 DB 里。**后续更新有两种方式**：

### 方式 1（推荐）：直接用线上 admin 后台编辑
- 登录 `/admin/guide`，点章节编辑，保存即生效（revalidatePath）
- **完全不需要再碰代码/部署**
- 适合：改正文、调文案、加/下架章节

### 方式 2：本地改 md → 重跑 seed（带 --force）
- 适合：大批量重写（如本次打磨 3 篇）
- 流程：本地改 `docs/agent-guide/*.md` → 重新打包上传 → 服务器 `pnpm db:seed:guide --force`（覆盖）
- ⚠️ `--force` 会覆盖线上 admin 手动编辑的内容，慎用

**结论：日常用方式 1（admin），大批量重写才用方式 2（seed --force）**。
