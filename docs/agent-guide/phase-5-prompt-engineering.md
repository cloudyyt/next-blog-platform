## Why 1：为什么 Prompt 是"接口设计"（不是咒语）

### 表面现象

新人改 prompt 一行字，输出 80% 变化。感觉"玄学"。

### 深层原因（Phase 1 已讲，这里回顾）

Prompt **不是在"教"模型新东西**，是**在激活模型在预训练数据里已经学到的能力**。

**这个事实的推论**：好 prompt 像好 API 文档，差 prompt 像口头嘱托。

### 一个对比（建立直觉）

**差 prompt**（口头嘱托风格）：
```
帮我总结一下这篇文章，要简短一点，专业一点，别太啰嗦
```

为什么差：
- "简短一点"——多短？50 字？100 字？
- "专业一点"——什么领域的专业？
- "别太啰嗦"——这是反向约束，没说正向该做什么
- 没示例
- 没失败兜底（如果文章是乱码怎么办）

**好 prompt**（接口设计风格）：
```
你的任务：将输入文章总结为一段中文摘要。

要求：
- 长度：80-120 字（含标点）
- 语气：新闻体，第三人称
- 包含：核心论点、关键数据、结论
- 不包含：作者主观评价、修辞、过渡语
- 如果文章是乱码或太短，输出：「无法生成摘要」

【文章开始】
{article}
【文章结束】

只输出摘要本身，不要任何前后缀说明。
```

为什么好：
- 输入输出定义清晰（输入：article / 输出：80-120 字摘要）
- 边界明确（"不包含"反向约束）
- 有失败兜底（"乱码或太短"→ 明确输出）
- 有约束（"不要任何前后缀"）

**这就是接口设计思维**：每个 prompt 都像在写一份 API 文档。

## Why 2：为什么 three 范式存在（不是历史包袱）

LLM 文献里常提三种 prompt 范式：
1. **Zero-shot**（零样本）
2. **Few-shot**（少样本）
3. **Chain-of-Thought**（思维链，CoT）

很多人把它们当历史演进的产物——错。它们是**三种本质不同的能力激活方式**，各有适用场景。

### Zero-shot：直接给指令

```
将以下文本分类为「正面/负面/中性」：
"{text}"
```

**本质**：完全依赖模型在预训练里学到的"分类"能力。

**适合**：模型已经熟悉、任务定义清晰、输出格式简单的场景（如情感分类、垃圾检测）。

**优点**：token 省、响应快、可迁移性强。
**缺点**：对模糊任务表现不稳定。

### Few-shot：给几个例子

```
将以下文本分类为「正面/负面/中性」：

例子：
"这家餐厅的菜很好吃" → 正面
"服务态度极差" → 负面
"价格一般般，没什么特别" → 中性

现在分类：
"{text}"
```

**本质**：用具体例子**对齐模型到你的输出格式和判断口径**。

**适合**：输出格式特殊、判断口径主观、任务复杂的场景。

**为什么比 zero-shot 稳定**：因为模型的注意力机制对"具体输入-输出对"的激活，远强于对抽象指令的激活（Phase 1 已讲）。

**缺点**：token 占用多；例子选不好反而误导模型。

### Chain-of-Thought：让模型"思考过程"

```
问题：小明有 5 个苹果，吃了 2 个，又买了 3 个，现在有几个？

请一步一步思考：
步骤 1：5 - 2 = ?
步骤 2：上一步结果 + 3 = ?
最后输出：{answer}
```

或更简洁的触发词：
```
问题：...
请一步步思考（Let's think step by step）：
```

**本质**：强制模型把推理过程**显式输出**，避免直接给答案时"跳步"出错。

**适合**：多步推理、数学题、逻辑题、复杂决策。

**为什么有效**：LLM 的"思考"和"输出"耦合——**只有输出过的内容，模型才能"真正利用"**。让模型"在心里想"不如让它在屏幕上写出来。

### 三种范式的选择决策树

```
任务复杂度?
├─ 简单分类 / 抽取 / 改写
│   └─ Zero-shot 先试，效果不够再加 Few-shot
├─ 输出格式特殊 / 判断口径主观
│   └─ Few-shot（2-3 个例子）
├─ 多步推理 / 数学 / 逻辑
│   └─ Chain-of-Thought
└─ Agent 决策（要调用工具）
    └─ ReAct 范式（Phase 4 + Phase 7 深入）
```

## Why 3：为什么 Prompt 80% 价值在前 20% 设计里

很多新人花大量时间"优化 prompt 一行字"。但严肃工程实践里：

> **prompt 的 80% 价值在最初的接口设计里就决定了——清晰的指令 + 1-3 个好的示例**。

剩下的 20% 优化（语序、用词、CoT 触发词）**必须靠 eval 集验证**，不能靠感觉。

### 反面教材

某自媒体文章："震惊！把 'Please' 改成 'Kindly' 让 GPT 准确率提升 30%"——这是**单样本观察**，不是统计事实。

### 正面方法

写完 prompt 后：
1. 在 eval 集上跑（至少 30 个样本）
2. 看准确率/通过率
3. 改一个变量（用词/语序/示例数），再跑
4. 用数据决定是否合并改动

**这是工程，不是炼丹**。

## Why 4：为什么 Promptfoo 是 Prompt 的"单元测试"

### 没有 eval 集 = 不可维护

假设你的 prompt 给 1000 个用户用了 3 个月。某天产品经理说"加一条：避免输出 emoji"。你改了 prompt——但**你怎么知道这改动没破坏原有的 80% 输出质量？**

答案：**没有 eval 集就无法知道**。这就是为什么 prompt 优化"凭感觉"会越改越烂。

### Promptfoo 是什么

[Promptfoo](https://www.promptfoo.dev/) 是开源的 prompt 评测工具，支持：
- 多 prompt 对比（A/B test）
- 多模型对比（Qwen-Plus vs Qwen-Max）
- 自动评分（基于规则 / LLM-as-judge）
- CI/CD 集成（prompt 改动跑 eval，回归保护）

### 最小 eval 配置

`promptfooconfig.yaml`：

```yaml
description: "文章摘要 prompt 评测"

prompts:
  - file://promms/summarize.md

providers:
  - openai:qwen-plus
    apiBase: https://dashscope.aliyuncs.com/compatible-mode/v1
    apiKey: ${DASHSCOPE_API_KEY}

tests:
  - description: "正常文章应生成 80-120 字摘要"
    vars:
      article: "..."
    assert:
      - type: javascript
        value: "output.length >= 80 && output.length <= 120"
      - type: contains-any
        value: ["核心", "数据", "结论"]

  - description: "乱码输入应输出兜底语"
    vars:
      article: "asdfghjkl12345"
    assert:
      - type: contains
        value: "无法生成摘要"

  - description: "短文章不应有'其次''最后'等过渡词"
    vars:
      article: "..."
    assert:
      - type: icontains
        value: "其次"
        negate: true
```

跑：
```bash
npx promptfoo eval
npx promptfoo view   # 打开浏览器看结果
```

**这就是 prompt 的单元测试**。改 prompt 时跑一次，立刻知道有没有破坏现有行为。

## 五个高频场景的稳定模板

下面五个模板是 2026 年工程实践里**反复验证过**的稳定结构。直接拷贝使用，按需修改。

### 模板 1：分类任务

```
你的任务：将输入文本分类到以下类别之一。
类别：{category_list}

判断准则：
- {criteria_1}
- {criteria_2}

{# Few-shot 例子 #}
示例 1：
输入："{example_1}"
分类：{label_1}
理由：{reason_1}

示例 2：
输入："{example_2}"
分类：{label_2}
理由：{reason_2}

现在分类：
输入："{text}"
分类（只输出类别名，不要其他）：
```

### 模板 2：信息抽取

```
你的任务：从输入文本中抽取结构化信息。

抽取 schema：
{
  "field_1": "类型 + 描述",
  "field_2": "类型 + 描述"
}

规则：
- 找不到的字段填 null
- 不要编造，文本里没有就不要填
- 输出严格 JSON，不要前后缀

【文本开始】
{text}
【文本结束】

JSON 输出：
```

### 模板 3：摘要生成

```
你的任务：将输入文章总结为一段中文摘要。

要求：
- 长度：{min_len}-{max_len} 字
- 语气：{tone}（如"新闻体，第三人称"）
- 包含：{required_elements}
- 不包含：{forbidden_elements}
- 如果文章过短或乱码，输出：「无法生成摘要」

【文章开始】
{article}
【文章结束】

只输出摘要本身：
```

### 模板 4：风格改写

```
你的任务：将输入文本改写为{style}风格。

参考示例（这是目标风格的样例）：
"{reference_example}"

规则：
- 保留原文核心信息
- 改变表达风格，不改变事实
- 不要新增原文没有的信息

【原文开始】
{text}
【原文结束】

改写：
```

### 模板 5：Agent 决策（ReAct）

```
你是{role_description}。

可用工具：
{tool_1_name}: {tool_1_description}
{tool_2_name}: {tool_2_description}

用户目标：{user_goal}

请按以下格式输出（严格遵守）：

Thought: 我现在想到什么
Action: {tool_name 或 "none"}
Action Input: {tool_args_json 或 "null"}
```

这个格式对应 Phase 4 的 Function Calling 循环和 Phase 7 的 ReAct Agent。

## 一个真实案例：把"差 prompt"重写成"好 prompt"

### 起点（差 prompt）

```
帮我从这篇文章里提取关键信息
```

### Review 视角（接口设计）

| 缺陷 | 解释 |
|------|------|
| 没定义"关键信息"是什么 | 模型各凭想象 |
| 没定义输出格式 | 可能是段落，可能是列表，可能是 JSON |
| 没定义失败兜底 | 模型遇到乱码会硬编 |
| 没有 few-shot | 没对齐判断口径 |

### 重写（好 prompt）

```
你的任务：从新闻文章中抽取关键信息，输出 JSON。

抽取 schema：
{
  "title": "string，文章主标题",
  "date": "string，YYYY-MM-DD 格式，找不到填 null",
  "location": "string，事件发生地，找不到填 null",
  "key_figures": "string[]，关键人物/机构名",
  "summary": "string，50 字以内摘要",
  "topics": "string[]，主题标签，最多 3 个"
}

规则：
- 找不到的字段填 null 或空数组
- 不要编造，文本里没有的不要填
- 输出严格 JSON，无前后缀

【文章开始】
{article}
【文章结束】

JSON：
```

### 效果差异

- **差 prompt**：每次输出结构都不同，无法用代码消费
- **好 prompt**：100% 输出可解析 JSON，可直接入库

## Prompt 工程的"反模式"清单

> **反模式 1：把 prompt 当咒语吟诵**
> "请用最专业最严谨最准确的方式..."——堆砌形容词。模型不会因为形容词多就工作得更好。

> **反模式 2：相信"神奇触发词"**
> "深呼吸"、"想一想"、"作为 AI 专家"——这些在单次实验里可能有效，但不是稳定提升。

> **反模式 3：在 prompt 里写"不要"清单**
> "不要啰嗦、不要 emoji、不要用第一人称、不要..."——反向约束太多会让模型困惑。改为正向约束（"使用第三人称"等）。

> **反模式 4：忽略输出长度限制**
> 不写 `max_tokens` 会导致模型偶尔输出几千字，token 成本爆炸。

> **反模式 5：不做 eval 就大改 prompt**
> "我感觉这样写更好"——感觉不可靠。改 prompt 必须跑 eval 集对比。

## 为什么"Prompt 工程师"不是一个独立的工程角色

2023 年曾短暂出现"Prompt 工程师"岗位定位。**2026 年这种角色已经基本消失**。

### 原因

1. **Prompt 是 Agent 工程师技能树的一项**，不是独立岗位
2. **真正难的不是写 prompt，是设计 Agent 系统**——工具调用、Memory、流程编排、评测
3. **把 prompt 工程当成"特殊技能"会限制成长**——你需要的不是"会写 prompt"，是"会做 Agent 工程"

### 正确定位

prompt 工程是 Agent 工程师的核心技能之一，和 Function Calling、RAG、可观测性并列。**不要把它当成独立方向，要把它融入整个工程能力栈**。

## 工程实践中常见的判断题

下面这些场景，是 prompt 工程实战里反复出现的判断点。想清楚这些，比背"最佳实践"更有用：

1. **"怎么写一个高质量 prompt？"**
   答：从"接口设计思维"切入，举一个具体例子（差→好的重写过程）。重点是清晰的输入输出定义、边界、示例、失败兜底。

2. **"prompt 跑出来的输出不稳定怎么办？"**
   答：从概率性本质讲（Phase 1），然后讲 schema 校验、retry、ensemble、降低 temperature、用 few-shot 对齐。

3. **"你怎么测试 prompt 的质量？"**
   答：Promptfoo + golden set + LLM-as-judge。改 prompt 必须跑 eval。

4. **"zero-shot 和 few-shot 什么时候用哪个？"**
   答：见本章 Why 2 的决策树。

5. **"如果让你给博客文章做自动摘要，你的 prompt 怎么写？"**
   答：用本章模板 3 + 加上"避免幻觉"的约束（"只基于原文事实，不要编造"）。
