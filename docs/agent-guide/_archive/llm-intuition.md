# LLM 原理直觉：token、上下文与幻觉

> 这一章也没有代码。它回答的是你之后每天都会遇到的那些"为什么"：
> 为什么账单按 token 算？为什么聊着聊着它就"忘了"开头说的话？为什么它会一本正经地胡说八道？

---

## 本章你将解决什么

读完这一章，你应该能：

- 用**账单直觉**理解 token：知道一句话大概花多少钱，上下文为什么是成本大头
- 区分**上下文窗口**和**训练知识**：一个像工作记忆，一个像出厂设置
- 解释**温度参数**在调什么，为什么温度 0 也不等于确定性
- 从机制层面说清**幻觉为什么必然发生**——以及为什么 RAG 是"止血带"而不是"根治药"
- 分清**推理模型**（DeepSeek-R1、o 系列）和普通模型的差别，知道什么时候值得多花钱
- 建立一张**能力边界清单**：什么活该交给 LLM，什么活交给它就是给自己埋雷

> 前置知识：读过术语地基（Embedding / RAG 两个词知道是什么即可）。
> 不需要数学，全程用前端工程师熟悉的东西打比方。

## Why 1：token 不是字符——你的账单和模型的"视野"都按它算

LLM 世界里没有"字符"和"词"的统一单位，只有 **token**。你可以把它理解成"模型的眼中的最小字块"：

- 英文里，一个 token ≈ 0.75 个单词（`hello` 是 1 个 token，`internationalization` 可能被切成 4-5 个）
- 中文里，一个汉字通常是 1-2 个 token（取决于分词器，主流模型大约 1 个汉字 ≈ 0.6-1 个 token）

**为什么你必须对它有直觉**——因为三样东西都按 token 计价：

| 按 token 计算的东西 | 你的体感 |
|---|---|
| API 账单（输入 + 输出都算钱） | 一次带 50 页文档的提问，可能比 50 次普通对话还贵 |
| 上下文窗口占用 | 塞满文档后，模型"视野"里没剩多少空间思考 |
| 速度（输出 token 是逐个生成的） | 输出 2000 token 的长文，就是比你想象得慢 |

一个实用的心算：**1 万字中文 ≈ 1 万多 token**。用 DeepSeek 这类低价模型，一次几千 token 的调用成本可以忽略；但如果做 RAG 每次都把几十页资料塞进上下文，日积月累就是成本大头。这也解释了一个工程事实——**RAG 系统的第一优化目标往往不是"更聪明"，而是"少塞点、塞准点"**（这个在《Agent 实战》RAG 篇会反复见到）。

## Why 2：上下文窗口是"工作记忆"，不是"硬盘"

这是新手最容易误解的概念。128K 上下文 ≠ 模型"记住"了 128K 的知识。准确的理解是：

> **上下文窗口 = 本次对话中，模型能"看一眼就想起"的内容上限。**
> 它像你的工作记忆——桌上摊开的资料就这么多，收走就忘。

由此推出三个工程事实：

**事实一：窗口很大 ≠ 每个字都被平等对待。**
模型对上下文中间部分的信息利用率偏低（所谓 lost in the middle 现象）。重要指令放开头和结尾，长文档里的关键页要做检索定位，而不是指望模型通读——这正是 RAG 存在的第一理由：**不是窗口不够大，是"全塞进去"既贵又不准**。

**事实二：对话越长，早期内容越容易被"挤出注意力"。**
多轮聊天中模型"忘了你十句话前说的话"，通常不是 bug，是上下文管理没做——要么历史被截断，要么关键信息没有以摘要/外部记忆的形式保留。《Agent 实战》LangChain 篇的"记忆"一章就是在解决这件事。

**事实三：训练知识 ≠ 上下文里的知识。**
模型知道"什么是 Docker"（训练时见过），但不知道"你们公司的部署流程"（没见过）。让前者走模型本身，让后者走上下文注入或 RAG——分清这两类知识来源，是设计一切 Agent 应用的第一刀。

## Why 3：温度——同一问题两个答案不是 bug

LLM 生成文本的机制是**逐 token 地从概率分布中抽样**。温度（temperature）控制这个抽样的随机程度：

- **温度 → 0**：永远挑概率最高的 token。适合代码生成、结构化输出、数据抽取——你要的是"标准答案"
- **温度高（0.8-1.0）**：分布被拉平，低概率词也有机会被选中。适合写文案、头脑风暴——你要的是"不一样"

两个必知细节：

1. **温度 0 也不等于 100% 确定**。采样之外还有浮点运算、批处理调度等非确定因素，同一 prompt 仍可能有微小差异。所以你写的任何"输出必须严格一致"的断言，在 LLM 面前都是赌博——这就是为什么结构化输出（JSON schema 约束）比"求求你输出 JSON"可靠得多。
2. **"创造性"是温度的副产品，不是智能的体现**。调高温度不会让模型变得更聪明，只会让它的选择更跳。让答案变好的正路是更好的上下文（RAG、few-shot），不是更烫的温度。

## Why 4：幻觉为什么必然发生——以及为什么 RAG 只是止血带

把幻觉理解为"模型在骗你"是错的。准确的心智模型是：

> **LLM 是一台"续写机器"。它擅长的是生成"统计上最像真话的话"，而不是"被验证过的话"。**
> 当它不知道答案时，它不会停下来——它会续写一个**格式完美的答案**。

前端类比：这就像一个只会 `JSON.parse` 不会校验的函数——不管喂什么，它都会尽力吐出一个看起来合法的结果。幻觉不是异常分支，是这个函数的默认行为。

三类典型幻觉场景，对应三种解法：

| 场景 | 本质 | 解法 |
|---|---|---|
| 问它冷门事实（某库某版本的行为） | 训练数据里没有/过时 | RAG：检索文档再回答 |
| 让它算数/数数 | 续写 ≠ 计算 | 工具调用：交给真正的计算器 |
| 让它引用来源 | 它会编造一个"看起来对"的引用 | 结构化输出 + 强制引用检索结果 |

注意一个关键的认知校准：**RAG 显著降低幻觉，但不能归零**。检索回来的资料模型仍可能读歪、过度概括。所以生产系统的完整答案是"RAG + 引用溯源 + 评测集持续监控"，这套东西在《Agent 实战》工程化篇的"RAG 深水区"一章展开。

## Why 5：推理模型——贵在哪里，什么时候值得

2025 年之后你会频繁遇到两类模型的选型：

- **普通模型**（DeepSeek-V3、GPT-4o、Qwen-Max）：收到问题，直接续写答案
- **推理模型**（DeepSeek-R1、o1/o3 系列）：收到问题，先生成一段"思考过程"（思维链），再给答案

直觉上的差别：普通模型是**脱口而出**，推理模型是**打草稿再说**。草稿要多花 token（贵、慢），换来的是在复杂推理任务上的显著提升：多步数学、代码调试、方案比选、复杂指令遵循。

选型经验法则：

- 分类、抽取、改写、简单问答 → 普通模型（快且便宜）
- 多步推理、复杂代码问题、Agent 的"规划"环节 → 推理模型
- 实际项目里常见的做法是**混用**：路由层用普通模型判断问题难度，难题升级给推理模型——这个模式你在《Agent 实战》的 LangGraph 篇会亲手实现

## 能力边界：一张"该不该交给 LLM"的清单

原理直觉最终要落到工程判断。记住这张清单：

**适合交给 LLM 的**（模糊输入 → 结构化输出）：
- 自然语言理解与生成、摘要、翻译、分类
- 非结构化信息的抽取和整理
- 需要大量"常识"的判断（这条评论是不是恶意）

**不适合的**（要确定性、要可审计）：
- 精确计算和账务（用代码）
- 强一致的业务规则（`if-else` 永远比 prompt 可靠）
- 需要负法律责任的事实陈述（必须挂检索来源 + 人工审核）
- "必须 100% 正确"的任何场景（LLM 的正确率是概率，工程只能逼近 100%，不能承诺 100%）

一个判断口诀：**能用 `if` 写出来的逻辑就别用 prompt；必须理解自然语言的地方才上模型。**
